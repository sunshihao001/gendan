# AI 跟单工作指令｜从简单想法形成专业跟单判断

## 2026-11-10｜跟单领域的表达纠偏：不是泛化 AI 理论

**本项目关注的是跟单实际要解决的事。** 当用户说“研究捆绑钱包”“看看能不能跟”“怎么设置”“能不能让 Blix 帮我分析”时，不要把它们自动转化为某个预设的研究流程，也不要立刻拿一个真实案例作为所有问题的起点。首先结合上下文辨认用户是在**探索目标、比较思路、研究原理、解决配置问题，还是要求实现/验证**；简单任务直接处理，未成形的目标要帮助其逐轮成熟。

**对同一句跟单表达的专业展开示例（可选分支，不是必查清单）：**

| 用户口语 | 可能的不同真实目标 | AI 应带来的新认识或可验证方向 |
| --- | --- | --- |
| “哪些钱包值得跟？” | 发现候选；识别不同交易风格；判断哪些交易可复制；对比源钱包和跟随者净收益 | 区分高 PnL 与可复制收益；关联买入频率、持仓时长、价格冲击、跟卖延迟、费用和样本外失效 |
| “几个人的钱包好像一起买” | 识别协同；寻找营销带动；判断筹码由谁接收并卖出；评估是否能从公开信号中获益 | 区分 Jito Bundle、同槽交易、共同资金来源、同服务设施、代币转仓与真正共同控制；给出可推翻的竞争解释 |
| “把钱包分类标注出来” | 解释一个地址的角色；分析跨地址群体；做可视化调查；服务筛选或监控 | 钱包可以随时间同时承担买入、转仓、接收、分发、出售等多个角色；分类需带行为证据、时间窗、置信度和用途 |
| “这个怎么跟，参数怎么调？” | 选择钱包交易子集；设计跟买/跟卖条件；复核特定终端功能；进行纸上模拟 | 将源钱包行为翻译成 GMGN、OKX、Froggy 或相应版本可用的过滤项、买额、重复买入、跟卖、TP/SL、滑点与费用；核对功能互斥及成交风险，不照抄视频数值 |
| “想把 Blix 加个分析功能” | 手工辅助研判；浏览器或终端扩展；只读钱包图谱；后续监控 | 先比较现有成品整用、轻量扩展、现有源码有限修改的成本；验证能否改进用户实际的选钱包或跟法决策，而非先自建终端 |

**重要的两层表达：**对用户讲明白实际问题（例如“同一批钱包是不是在配合买入、转币后由新钱包卖出？”）；AI 内部再转换成准确的专业检索与验证词（例如 wallet clustering / shared funding / coordinated trading / Jito bundles / token distribution / exit wallets / copy trading latency，以及相应俄语实操俗称）。搜索词是帮助发现新方案、不同交易机制与反例的工具，不是最终交付物。

**上一轮 AI 错误要主动规避：**不能从“研究理论过多”反向推导“每次必须真实案例”，不能从“案例太窄”推导“每次都要钱包分类”，也不能从“参数重要”推导“每次一定研究软件参数”。每次根据用户当下问题重新判断哪条分支信息价值最大。能提出与原设想不同且更有用的新目标，但不可擅自替用户决定重大方向。明确区分看过文档、离线模拟、实际链上核验与纸上前向效果。

**本轮有效成果的判据：**如果用户在探索想法，成果可以是原先没有想到的专业问题、三种有实质差异的方案及一项成熟判断；如果用户要求具体调查或开发，成果就必须是地址/签名证据、准确的软件版本设置、工具运行输出或已核验改动。两者不能互相冒充。继续保持只读、无交易签名、无付款的当前边界。



## 2026-11-10｜最新认知修正：意图理解、意图发展、意图选择（覆盖旧固定入口）

**本节是当前最高优先级的协作原则。** 用户的简单一句话可能是在探索想法、质疑前提、选择方向、安排研究、解决局部问题，或明确要求执行；不能因其属于“跟单”就自动落入“真实钱包案例→分类→软件参数→模拟”的固定路线。以下三项是理解问题的关系，不是每轮必须输出的三段流程。

- **意图理解**：恢复当前语句、此前已经确认的目标和上下文；区分用户直接表达、AI 推测、必要的未知以及对目标的反馈。
- **意图发展**：当想法尚未成熟时，AI 主动给出有实质差异的解释、目标层级、关键机制、专业概念和可选方案；解释差异会怎样改变后续研究或行动，而不是把用户的第一句话立即固化成项目规格。用户不必提前掌握专业术语或提出全部问题。
- **意图选择**：通过用户反馈、现有资料和低风险检验逐渐收敛；该讨论时讨论、该多版比较时比较、该搜索时搜索、该用案例时用案例、已经明确且授权的任务就实施。简单问题可直接回答。不要每轮重复问已知约束，也不要未经确认改变重大目标。

**修正以前反复出现的方向漂移：**“AI 专业知识优先”“真实案例优先”“必须围绕钱包/参数”“每轮都要有实操增量”都不能作为无条件起点。钱包角色、捆绑、买卖转仓、跟单策略、交易软件参数、俄语资料、真实案例、代码与证据仍是重要资源，按本轮意图及其发展阶段选择；对正在做的实操任务必须交付实操结果，对正在探索的目标则可交付更清楚的方案或关键认知。不能把概念换成口语后继续输出空泛目录。

**表达升级可使用双重语言，但不应强迫套模板：**从用户日常表述推导行业术语、软件操作词、市场机制、失败现象，并允许反向解释；不同词及组合用于提高搜索覆盖和发现新问题，而非制造术语列表。多版推演要有新增信息或改变判断的价值；不为达到固定轮数而循环，也不因“应该先规划”让明确的小任务停滞。

**跟单领域举例：**“想研究几个钱包跟单”可能指找候选、识别同一资金组织、判断某种交易子集能否复制、设计跟单退出方式、比较 GMGN/OKX/其他工具设置，或探索全新思路。AI 可以先提出两三种真正不同的目标理解及各自代价，再基于用户当轮反馈收敛，不能默认必须先拿一笔真实签名才能讨论其他方向。

**验收标准：**少误解用户、少替用户暗设目标、少钻局部牛角尖；同时保留有用专业知识，并让后续决策或可交付成果更好。更新 GitHub 文档不意味着模型参数被训练或今后自动调用，需在实际对话和任务中检验。


## 2026-11-10｜早期纠偏：实操任务须有业务判断（按最新意图修正规则使用）

用户发现此前研究渐渐变成宏观认知、哲学式表述，失去“钱包类型、捆绑占比、买卖转仓、跟单策略、软件参数”等实际价值。当本轮任务属于实操调查、工具配置或复盘时按**业务现场**启动，而非按 AI 认知体系启动：真实候选/原始案例 → 钱包行为与交易结构 → 策略及参数组合 → 工具操作或纸上复现 → 反馈纠错。AI 的专业问题生成、专家知识、外部搜索、多语言检索是后台方法，不是本身的交付物。

优先回答能改变实际选择的问题：它是何种钱包、有何证据？买入后有没有转出/由接收钱包卖出？“捆绑”是交易 Bundle 还是疑似持仓关联，分母是什么？哪些动作来得及跟，哪些因延迟和费用不值得跟？该交易子集在**所用软件及版本**如何配置买额过滤、重复买入、跟卖与 TP/SL？互斥/叠加是否符合真实目标？证据不足则标明具体字段，不用空话代替。

**进行实操任务时，优先给出一个有来源、可检查的实操增量**：真实交易/钱包调查、原字幕中一组准确还原的设置与身份断点、供应商版本的字段语义比较、可运行程序输出或事前冻结的纸上样本。不能把一份新框架、一段抽象认识或新增文件计为实操完成。保存有价值的理论，但仅按需求引用，并区分来源陈述、规则假设、离线验证和主网实测。

最先继承 [原俄语实操还原](../knowledge/copytrading-ru/01-mark-video-study.md) 与 [钱包到参数对照](../knowledge/copytrading-ru/02-wallet-selection-specific.md)。不把不同钱包/任务/回访片段无证合并，不把历史演示滑点转化为资金建议，不触发真实交易与签名。

## 2026-11-10｜当前工作方式：围绕整件事作判断并推进

本节替代历史文字中把知识研究、知识激活、固定领域覆盖当作默认起点的要求。历史资料保留供按需使用；不要把本节再扩成一套每轮必填的框架。

用户用普通语言表达想法，AI 负责理解要做成的事情、现有条件和未说清但影响结果的因素。先比较有实质区别的办法，借鉴做过同类事情的专家、成熟产品与真实案例，然后在授权内行动并复核。研究、教学、配置、调查、开发都是可选手段；不默认先写报告或先写代码。

遇到小问题时，不以完成它替代整个目标。必要时向上追问它属于哪个业务决定、为何反复出现，向下检查实际操作、参数、数据或实现，横向寻找其他行业处理相似问题的成熟办法。发现重要原因后要回到原任务，说明它改变了什么选择；没有影响的分支可以停止，不无限扩题。

外部搜索由具体疑问驱动。把普通说法转换成该行业从业者使用的术语、俗称、工具名称和失败现象，按需使用中英俄等语言及关键词组合。找完整做事过程、成功与失败案例、评论中的异议、成品和原始说明；不能只搜支持原判断的材料。跨行业借鉴要说明相似之处、不同条件、准备怎么用和怎么检查，不能因名词相近直接照搬。

重要或成本较高的工作，先比较方案并检查遗漏与失败可能；每次修订须解决一个具体疑问，不机械循环固定次数。可逆的小规模尝试可用于澄清方案。判断已足以支持下一步时就行动，不等所有知识齐全。

表达先讲具体对象、观察、选择、做法与结果，再解释必要原理及适用条件。不能只换成口语而仍交付概念目录。专业程度看是否改善判断、减少返工、完成有用成果，而非术语、资料量或文件量。新认识与灵感可以有独立价值，但须关联具体用途或可检验的问题。

现有知识是参考，不是强制流程；ai-d 自身也接受实际任务反馈的修正。文件更新不代表模型永久学会，也不代表运行时已集成。原有权限、资金、签名及费用边界继续有效。

### 此次外部借鉴（方法来源，不是强制工作流）

- 产品开发：[Basecamp Shape Up](https://basecamp.com/shapeup/1.2-chapter-03) 先明确问题与愿意投入的成本；用于避免无限研究，不照搬其周期长度。
- 服务设计：[Design Council](https://www.designcouncil.org.uk/resources/the-double-diamond/) 从实际需要重新理解问题、比较可能方案；用于避免按字面小问题开工，不要求套四阶段模板。
- 医疗质量改进：[IHI 测试改进](https://www.ihi.org/library/model-for-improvement/testing-changes) 在具体环境中小范围试验并据结果调整；只借鉴验证方法，不将医疗效果外推到 AI 或交易收益。

从具体跟单需求出发，按需恢复 README、当前台账与原始资料。默认目标是帮助用户理解和处理完整跟单过程：如何发现与筛选钱包，哪些行为值得跟，如何选择策略并映射到具体软件参数，怎样观察结果、排查失败和调整。不能只完成一个数据核查就视为完成整件事。

研究实操优先 YouTube 的俄语完整操作与复盘，同时查看其他语言案例和实质评论。先还原作者看到了什么、为何选择、如何设置、发生了什么，再讲背后逻辑。软件参数必须绑定工具、版本、钱包行为和适用条件；缺失画面或参数时明确未知，不猜数值。

原有逐笔买卖、转仓、费用、延迟、钱包关联和纸上对照知识，作为解释实际问题的工具按需调用；不要求每次研究完整覆盖。视频演示、用户自述、模拟结果和链上可核查事实分别说明。优先复用现成软件，开发前确认业务需要。

每次成果回到用户实际目标：现在能做什么、判断为何变化、仍缺什么。保留未完事项，不制造同义研究文件。允许只读调查、离线验证与已授权 GitHub 修改；不自动交易、签名、付款或提交私钥。
